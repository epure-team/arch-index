# 3.12 — the crash-surface regression verb: design before code

**Date:** 2026-09-05
**Status:** design, not implemented. Parsing area is held by PR #73.

## The question the design has to answer first

`arch-rules` evaluates fitness functions over **one** index. A regression gate
compares **two states**. Those are different shapes, and picking the wrong one is
how this item would ship something that looks like a check.

The existing ratchet (`tezt/tests/must_null_ceiling.ml`) resolves it by storing a
number in a test. That works for one scalar and does not generalise: the crash
surface is a **set of sites**, and a scalar over a set loses exactly the
information a reviewer needs — *which* site appeared.

## Decision: an ALLOW-LIST, not a baseline

The rule states the invariant absolutely, and the sites already accepted are
named explicitly:

    rule "protocol entry points gain no new fatal origin"
      forbid origin from file:src/proto_alpha/lib_protocol/main.ml form:assert,division allow-file:crash-allow.txt

**Measured, and it is what makes this viable:** the list is 20–38 entries for
realistic roots — `main.ml:*` 37, `apply.ml:*` 33, `validate.ml:*` 20, and 38 at
whole-Octez scale on the same root. Small enough that a human reads the whole
list in a review.

### Why an allow-list beats a baseline file

- **It is reviewed like code.** Accepting a new fatal origin becomes a diff with
  a name on it, not a regenerated blob.
- **It sidesteps the three-cause trap** that I found by building the baseline
  gate and getting it wrong. A site list can grow for three reasons — a real
  regression, widened coverage, or a site whose proof strengthened `MAY → MUST` —
  and a line-diff conflates all three. Comparing against a **declared set keyed
  on site identity** (`function | file:line | form | exn`, never the MUST/MAY
  marker, which is a proof strength and not an identity) makes the third cause
  invisible and forces the second through a human decision.
- **There is no "coverage grew, auto-pass" branch to get wrong.** With a
  baseline, widened coverage has to be detected and excused automatically; with
  an allow-list the human always adjudicates, which is the correct place for that
  judgement.

### The costs, stated

- **The rule fails on our own progress** until someone extends the list. That is
  the intended behaviour — a newly-visible fatal origin is exactly what a person
  should look at — but the failure message MUST distinguish it, by reporting the
  coverage delta alongside the new sites. Without that the failure reads as a
  regression and someone disables the rule.
- **No `--regenerate` flag, ever.** An allow-list that can be regenerated by a
  command is a baseline with extra ceremony: people will run it blindly and the
  review property evaporates. Extending the list must cost a deliberate edit.

## Why `allow-file:` and not continuation lines

`bin/arch_rules/arch_rules.ml` enforces **one statement per rule** and dies with
*"rule already has a body"* on a second line. Continuation lines would change
that structural invariant, in the parsing area PR #73 currently holds. A
`allow-file:` token keeps the invariant, adds one `match` branch, and puts the
list where it is most reviewable — its own file.

## Selector kinds this verb serves, declared

Stated explicitly because of the defect the #73 review found in `Dep`: it
**discards the selector kind** and globs the pattern against strings, so
`forbid dep from fn:foo to file:bar` is accepted and silently reinterpreted.
A verb that does not declare its kinds inherits that by omission.

`forbid origin from <sel>` accepts **`file:`** and **`fn:`** only.
`module:` and `ext:` are REFUSED at parse time with a message naming the two
accepted kinds — an origin belongs to a function in a file; a module is not a
root and an external has no body to hold one.

## Both open questions are now answered

**`allow-file:` is the right form.** `kind:` is the only `token:value` outside
selectors, matched by `String.sub k 0 5 = "kind:"` and then sliced — this is the
same mould. Confirmed in the source.

**And the entry format is the four declared fields, NOT the query's rendering.**
My reason was the `top_reason` string/constructor divergence. The parsing-area
owner supplied a better one, measured an hour before: **the rendering is pinned
by no test.** `Arch_graph.label` strips the `ext:` prefix at
`arch_graph.ml:206-207`; disabling that strip leaves the whole suite green at
164/164, and the only occurrence of `ext:` anywhere in `tezt/tests/` is a
*comment* in `must_null_ceiling.ml`. Verified here independently.

So coupling a CI gate's allow-list to that rendering would build the gate on the
one surface of the system nothing retains. Any display-format improvement would
silently invalidate every exemption — and **an invalidated exemption does not
read as an error, it reads as a new site, i.e. as a regression.** That is the
three-cause confusion coming back through the back door after being chased out
the front. The translation cost is the price of decoupling, and it is explicit.

## Two parser properties that bite a FILE PATH specifically

Both verified in `bin/arch_rules/arch_rules.ml`, both undocumented.

**1. A `#` anywhere in the line truncates it, silently.** Comment stripping is
`String.index_opt raw '#'` at line 102 — the FIRST `#`, wherever it sits. So
`allow-file:sites#1.txt` becomes `allow-file:sites` and the rule loads a file
that does not exist, or worse, one that does. **It fails by deletion**, the same
family as backticks eaten by bash inside a double-quoted `-m`.

**Decision: refuse a path containing `#`, with a message that names the
character.** Not "document that it is impossible" — a documented impossibility is
still a silent truncation for whoever did not read the doc.

**2. `String.split_on_char ' '` (line 125) turns a path with a space into an
extra token**, which falls into the catch-all `die "unrecognised rule body"`.
Closed and loud, so not dangerous — but the message will not tell the author that
the cause is a space in their path. **Decision: name that possibility in the
refusal text.** One clause, and it converts a puzzling failure into an obvious
one.

## Harness note, inherited from the #73 review

When mutation-testing this verb, the binary whose hash must move is
`arch_rules.exe`, **not** `tezt/tests/main.exe`: the tests drive the CLI as a
subprocess, so the test binary's md5 is unchanged by a `lib/` or `bin/` mutation
and every mutant would read as a false survivor.
