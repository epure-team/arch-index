# Step 2 clarifications — functor-instance-resolution

| Q | A |
|---|---|
| Does the catalogue describe runtime functor instances or every application that could occur across a project? | No. It describes syntactic functor-application occurrences found while successfully decoding the explicitly selected OCaml implementation CMTs. It MUST NOT imply runtime multiplicity, a closed world, or coverage of unselected, failed, interface-only, or external artifacts. |
| Which typed-tree nodes are catalogue occurrences, and how are nested or chained applications covered? | Each encountered `Tmod_apply` and `Tmod_apply_unit` within the supported implementation-CMT walk is in scope. Since ordinary applications retain both functor and argument module expressions recursively, nested/chained applications must preserve their source order and structure rather than being flattened into one inferred instance. The exact parent/child or ordinal representation is [OPEN]. |
| What exact classifications and diagnostics are emitted for named, anonymous, constrained, unit, and unsupported functor/argument expressions? | The brief requires all of those shapes to remain distinguishable and unsupported shapes to carry explicit diagnostics; existing dependency and alias collectors cannot supply that classification because they deliberately reject applications and several non-identifier expressions. The closed classification vocabulary, constraint-unwrapping rules, and diagnostic codes/messages are [OPEN]. |
| What fields constitute one persisted catalogue row and the documented `arch-query functor-applications` output? | Source provenance, application structure, argument kind, nested order, and diagnostic state are required; producer-run provenance is the existing normalization pattern. The exact relational columns, nullability, displayed columns, filtering/limit options, and stable text format are [OPEN]. |
| How is an occurrence identified when binders are shadowed, locations are ghost/exceptional, or synthetic nodes share a position? | Visible names or source position alone are insufficient. `Ident.unique_name` may distinguish shadowed binders during one artifact walk, while `module_expr` has no UID and compiler stamps MUST NOT be advertised as cross-build-stable persisted identity. The deterministic composite key, collision discriminator, and behavior for unusable locations are [OPEN]. |
| When may the catalogue completion marker be earned, especially if an artifact fails, is unsupported, lacks a source path, or an insertion is rejected? | Row presence or a successful process exit is not enough. The marker must be cleared before rebuild and earned only according to an explicit collection contract; an absent marker must make the query refuse rather than print a misleading empty result. Whether a run with any skipped/failed artifact or rejected catalogue insertion is incomplete, and the precise complete/partial/unsupported state model, are [OPEN]. |
| May catalogue collection alter the existing CMT producer tuple, definition traversal, or graph-analysis data flow? | No observable graph contract may change: one function remains indexed per static definition; applications create no cloned `M.%` definitions; existing `pending_call` semantics, call/dependency rows, completion markers, TOP reasons, edge forms, and query verdicts remain unchanged. Research identifies the current public `process_cmt` result as an exact three-list tuple consumed by the main run, so catalogue plumbing must preserve that existing public call API rather than silently turning it into a four-list contract. |
| Which schema and lifecycle surfaces may change? | Only the main SQLite schema is in scope. The change is additive from main schema version 1.13 (with the next version rechecked against main at shipping); flat schema 1.3, LSP, MCP, and UI remain unchanged. Every new producer-owned table must participate in deterministic reindex drop/recreate, and every new presence-bearing marker must use the centralized clear/re-earn lifecycle and its mechanical tests. |
