# Adversarial challenges — functor-instance-resolution

1. **C-1 [US-1]:** The story requires every immediate application visited in the selected implementation Typedtree, including applications in functor bodies, anonymous arguments, unnamed bindings, and expression-local modules, but it does not define the complete traversal boundary (for example, whether module expressions reachable through unpacked expressions, object/class expressions, extensions, or other expression subtrees are included); what exact syntactic containment rule determines whether an application occurrence must be catalogued?
2. **C-2 [US-1]:** An `application` descriptor references a local occurrence ordinal while ordinals are application-only preorder with the functor operand visited before the argument operand, but the contract does not state whether the containing application receives its ordinal before either child or how forward references are represented; which precise ordering and referential-integrity rule governs nested forms such as `F(A)(B)` and `H(F(A))`?
3. **C-3 [US-1]:** Public occurrence identity is “artifact identity within this run plus preorder ordinal,” yet artifact identity is not defined when the same CMT is discovered through duplicate paths, symlinks, copied artifacts, or colliding normalized paths; what exact selected-input identity and deduplication rule prevents either collapse or double counting?
4. **C-4 [US-1]:** Reindexing the same database must produce stable public identities and ordered output, while the observable rows also expose producer-run provenance, which may contain a new run id or time-dependent data on every rebuild; which exposed fields are covered by byte/value stability, and how can run provenance vary without contradicting that guarantee?
5. **C-5 [US-1]:** The catalogue admits source-backed applications only, but selected inputs may have `missing_source`, `dropped_module`, or `collection_failed` outcomes and only collected inputs contribute rows; the exact point at which an input becomes “selected,” the distinction between these outcomes, and whether a CMT with partially collected rows can be recorded as failed are unspecified, making completeness and rollback behavior ambiguous.
6. **C-6 [US-1]:** Diagnostics must distinguish opaque head, anonymous argument, unpacked expression, and unusable location, but the requirements do not define whether diagnostics attach to the occurrence, head, argument, or nested descriptor; whether multiple codes may coexist; or their deterministic order, so equivalent facts could persist and render differently.
7. **C-7 [US-1]:** “No graph change” is expressed as retaining previous graph semantics, but schema version, producer-run rows, warnings, transaction boundaries, and catalogue failures can affect indexing without changing `calls`; which exact observable compatibility snapshot—definitions, calls including all classification fields, existing completion markers, query verdicts, and failure behavior—must remain invariant?
8. **C-8 [US-2]:** A valid marker requires a nonempty selection with every selected input collected and all required provenance/rows stored, but the contract does not say whether marker earning and catalogue rows/outcomes share one transaction or what database state must remain after interruption, rejected persistence, or failure between row commit and marker write; without this, stale rows or a stale capability claim can survive rebuild failure.
9. **C-9 [US-2]:** The query must refuse on “inconsistent required data,” but the consistency predicate is undefined: it could include marker/schema agreement, outcome cardinality, selected-versus-collected counts, producer-run linkage, unique artifact/ordinal keys, nested ordinal references, location invariants, diagnostic vocabulary, or JSON validity; which violations are mandatory refusal conditions?
10. **C-10 [US-2]:** Legacy/flat schema, absent marker, partial coverage, and missing/inconsistent data all require a “named refusal,” but neither the stable refusal names nor precedence when several defects coexist is specified; tests and downstream callers cannot know which stderr/exit-3 contract to rely on.
11. **C-11 [US-2]:** The command promises a summary followed by application rows across table modes and two JSON arrays, while descriptors and diagnostics are themselves JSON-valued text cells; exact columns, null representation, escaping, headers/separators, JSON array ordering, and the meaning of `total` versus `returned` under invalid stored descriptors remain unfrozen, despite the intake making output fields a design obligation.
12. **C-12 [US-1, US-2]:** Prior art: OCaml Typedtree retains complete functor and argument expression structure in `Tmod_apply` (OCaml 5.5 `typedtree.mli`), whereas the stories persist shallow tagged descriptors for structures, unpacks, and functor literals and nested references only for applications; justify the information-loss boundary and specify which Typedtree structure must remain observable, especially given that local OCaml 5.3—not the cited 5.5 interface—is authoritative.
13. **C-13 [US-1, US-2]:** Prior art: OCaml `Path.Papply` structurally represents applicative paths (OCaml 5.5 `path.mli`), whereas the stories use artifact-local syntactic occurrence ordinals and treat rendered paths only as display provenance; justify rejecting path-based application identity/structure and define how a `Tmod_ident` whose resolved path contains nested `Papply` is catalogued without either losing the application or falsely presenting it as an observed application occurrence.
14. **C-14 [US-1, US-2]:** Prior art: OCaml Shape tracks definitions through module operations and functor application and can reduce to UIDs, aliases, stuck identities, or approximations (OCaml compiler-libs 5.5.1 Shape), whereas Shape-based reduction and target inference are explicitly excluded and the stories expose only syntax; justify this divergence and state the observable boundary that prevents Shape-like identity or approximation claims from leaking into descriptors, diagnostics, completeness, or future-readiness claims.

## Edge Cases

- **EC-1 [US-1]:** A parent application contains applications in both its functor and argument operands → each syntactic application is recorded exactly once with a deterministic parent/child ordinal relationship; the parent-versus-child ordinal assignment is otherwise unspecified.
- **EC-2 [US-1]:** The same physical CMT is selected twice through distinct path spellings or symlinks → expected deduplication and artifact identity are unspecified.
- **EC-3 [US-1]:** Collection fails after some occurrences from one input have been accumulated or persisted → whether partial rows are rolled back, retained with a failed outcome, or rejected wholesale is unspecified.
- **EC-4 [US-1]:** A ghost location has syntactically valid coordinates, or a non-ghost location has an empty filename, inverted range, or exceptional line encoding → the exact nulling and `unusable_location` rules are unspecified.
- **EC-5 [US-1]:** A resolved `Tmod_ident` path contains `Path.Papply` although no corresponding `Tmod_apply` node occurs in the selected tree → expected catalogue representation is unspecified and must not imply an observed runtime or syntactic occurrence.
- **EC-6 [US-2]:** A database has the v1 marker and required tables but an application descriptor references a nonexistent ordinal → query refuses with exit 3, no stdout, and a stable named inconsistency diagnostic.
- **EC-7 [US-2]:** A failed reindex begins from a previously complete catalogue → the old marker must not remain authoritative; whether old catalogue rows remain inspectable through SQL is unspecified.
- **EC-8 [US-2]:** More than one refusal condition is present, such as a legacy schema plus absent marker plus malformed descriptor JSON → exit 3 and no stdout are expected, but diagnostic precedence is unspecified.
- **EC-9 [US-2]:** `limit` exceeds the platform or SQLite row-limit representation while remaining decimal digits → whether this is an exit-2 overflow or a valid request is unspecified.
- **EC-10 [US-2]:** A valid catalogue contains zero applications and `limit0` is used in JSON mode → exactly one summary array entry and an empty application array are expected, with `total=0`, `returned=0`, and `truncated=false`.
