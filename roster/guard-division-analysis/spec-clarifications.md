# Clarifications — guard-division-analysis

Prepared from the validated intake and `spec-research.md` before story drafting. The fixed
parts below are source-backed constraints; `[OPEN]` marks decisions those sources require the
spec to freeze but do not themselves determine. Root must resolve every `[OPEN]` before stories.

| ID | Question | Answer from brief/research |
|---|---|---|
| Q-1 | What is the exact supported boundary for function parameters, parameter patterns, `function` cases, and case guards? | Each nested or top-level function is an entry with unknown parameters/captures. Optional/default-argument semantics are excluded. `[OPEN]` Which typed identities are seeded as unknown; whether ordinary irrefutable scalar parameter patterns bind usable facts; whether refutable patterns/cases are wholly unsupported or may make arms unreachable; whether pure zero-comparison case guards refine the RHS and subsequent cases; and whether an optional default makes only its expression, the whole function, or dependent sites unsupported. Ordinary labelled parameters without defaults also need an explicit ruling. |
| Q-2 | Does a nested function inside an unsupported construct start a fresh analyzable entry, and how are captures represented? | A nested function never inherits an outer branch execution guarantee and its parameters/captures cannot inherit outer numeric facts. Bindings created wholly inside it may be tracked only if its entry is supported. `[OPEN]` Whether free scalar captures enter as abstract top or as unsupported dependencies, and whether a function textually nested under a loop, handler, effectful region, or optional default starts fresh or remains `UNSUPPORTED`. |
| Q-3 | Which local binding and pattern forms are supported? | Compiler identifier identity, not source spelling, must key locals and shadowing. Immutable scalar `let x = e` and aliases are required; recursive evaluation is excluded. `[OPEN]` Semantics for alias patterns (`p as x`), tuple/record/constructor destructuring and literal projection, refutable `let`, or-pattern facts, simultaneous nonrecursive `and` visibility, and whether every recursive value group is wholly `UNSUPPORTED`. |
| Q-4 | What is the closed predicate and arithmetic vocabulary? | Direct native-int div/mod, constants, immutable locals/aliases, sequencing, pure `if`, zero equality/inequality guards, and basic int arithmetic are required. Guards must use compiler-resolved primitives and confirm native-`int` operand types. Transfers must conservatively model both 31- and 63-bit modular semantics; overflow may widen to top and concrete zero division must never run. `[OPEN]` Exact primitive list and operand shapes for negation/add/subtract/multiply/divide/remainder; accepted reversed guards and wrappers/negation; constant-folding versus abstract transfer rules; and behavior of `if` without `else`. |
| Q-5 | Which opaque calls or structural/effectful expressions return top, and which poison an execution region as unsupported? | Unknown ordinary calls are not expanded and return top; no heap facts survive. Loops, recursive evaluation, exception handlers, effects, mutation/heap reasoning, and optional/default semantics are outside the interpreter, and sites in unsupported execution regions stay `UNSUPPORTED`. `[OPEN]` The closed syntax boundary between a supported expression that consumes an opaque top-valued call and a call/construct that makes the enclosing or dependent region `UNSUPPORTED`, including evaluation-order treatment when exceptional or diverging expressions precede a site. |
| Q-6 | How are partial, nested, holed, and over-applied primitive applications inventoried and classified? | All eight int-family div/mod primitive identities belong in the syntax inventory. A native-int operation with fewer than two supplied original operands is not an executed division and is `UNSUPPORTED`; other integer families are inventoried but `UNSUPPORTED`. `[OPEN]` Whether an absent expression in an existing slot differs publicly from a missing slot; how nested later saturation is recognized and whether it yields one site or two; treatment of over-application and impossible labelled/optional holes; and which node supplies the occurrence location. |
| Q-7 | What is the stable public site identity, location schema, and total sort key? | Output must be stable and sorted, scoped to each accepted artifact, and include input path/digest/module plus site location, primitive, operand category, semantic status/reasons, and census. Compiler binder identities may be used internally. `[OPEN]` Whether location comes from the full application, primitive head, or divisor; exact start/end filename/line/byte-column/`pos_cnum`/ghost/line-zero fields; deterministic disambiguation for identical locations; the identity tuple and within-location ordinal; and whether `Uid.t` or `Ident.unique_name` is forbidden from public JSON because it is not established as cross-build stable. |
| Q-8 | What exact CLI/output/resource contract must be frozen? | Inputs are explicit repeatable CMT paths; canonical physical paths are deduplicated, symlinks rejected, duplicate module/source identities rejected, content is hashed before/after read, and only compatible complete implementation artifacts are accepted. Reports go to stdout only. Complete successful analysis exits 0 even with `ZERO`, `MAY_ZERO`, or `UNSUPPORTED`; command/input/internal failures exit 2 with diagnostics and no complete JSON. `[OPEN]` Flag names and text/JSON selection, closed JSON field types/enums and schema version, diagnostic channel, deterministic input/site ordering, maximum input/artifact/site/expression/state/time/memory bounds and the failure behavior for each bound. |

## Non-negotiable interpretation shared by all resolutions

Syntax inventory is a separate complete pass over accepted CMT implementations, so semantic
pruning cannot hide recognized sites. `ZERO` means the divisor is zero whenever that site is
reached under modeled conditions, not that execution is guaranteed; `MAY_ZERO` is potential,
not a confirmed failure. `UNREACHABLE` may arise only from causes explicitly admitted by the
bounded model, while unsupported regions may never be relabeled `NONZERO` or `UNREACHABLE`.
An empty inventory is an explicit observation about supplied artifacts, never a safety claim.
